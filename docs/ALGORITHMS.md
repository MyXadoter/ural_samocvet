# Алгоритмы и метрики

[Документация](README.md) · [Архитектура](ARCHITECTURE.md) · [Ограничения](VALIDATION.md)

Описание относится к функциям [dist/app.js](../dist/app.js). Это эвристики; глобальная оптимальность не гарантируется.

## Ограничения автоматического назначения

Для новой работы инженер должен быть на линии, иметь совместимый навык и, если он задан, точный требуемый транспорт. Заявка добавляется после предыдущей работы и переезда:

```text
начало = max(конец предыдущей работы + переезд, начало окна)
конец = начало + длительность
конец <= конец окна заявки
конец <= конец смены инженера
```

Следовательно, **всё время работы должно помещаться в окно**. Допускается ожидание до его начала. Первый переезд идёт от стартовой точки инженера. Возвращение на базу не добавляется.

Навык сопоставляется без учёта регистра по вхождению строк; транспорт — строгим равенством. Даты не учитываются, расчёт ограничен одной условной сменой без перехода через полночь.

## Время пути

При доступной матрице OSRM используются профиль `driving`, метры и секунды. Время переводится в минуты округлением до ближайшего целого с минимумом 1 минута. Профиль одинаков для всех видов транспорта.

Без матрицы `fallbackLeg()` берёт геодезическое расстояние, умножает его на 1,28 и оценивает движение со скоростью 28 км/ч. Время округляется до ближайшей минуты, минимум — 4 минуты. Это расчётное допущение, не измерение реального пути.

## Baseline

`planBaseline()` сортирует заявки по началу окна, при равенстве — по убыванию базового приоритета. Заявка назначается первому инженеру в исходном порядке, которому её допустимо добавить в конец маршрута. Если такого нет, она остаётся нераспределённой. Локальные улучшения к показываемому baseline не применяются.

## Regret‑2

На каждой итерации для каждой оставшейся заявки `choicesFor()` рассчитывает варианты **добавления в конец** совместимых маршрутов. Вставки во все промежуточные позиции на этом этапе не перебираются.

Стоимость допустимого варианта:

```text
c = переезд_мин + 1,8 × переезд_км
    + 0,15 × max(0, начало_работы − начало_окна)
    + штраф_за_резерв
```

Штраф равен 35 для резервного инженера при отсутствии `авари` в типе/категории заявки, иначе 0. Варианты сортируются по стоимости. `regret = c₂ − c₁`; при единственном варианте — 1000, при отсутствии — −1. Выбирается заявка с максимальным regret, затем критичностью `K`, затем ближайшим окончанием окна. Ей назначается вариант `c₁`; после этого варианты остальных заявок пересчитываются.

### Критичность

`K = базовый приоритет + окно + дефицит навыка + длительность + технология`.

| Компонент | Правило |
|---|---|
| Базовый приоритет | Первое совпадение в категории и типе: `авари`/`глобаль` → 100; `нет линка`/`разрыв` → 80; `локаль` → 65; `нов`/`заявка на подключ` → 50; `конвер` → 45; `дозаказ` → 30; иначе 20 |
| Окно | До 60 минут включительно +10, до 120 +5, иначе 0 |
| Число совместимых доступных инженеров | Не более одного +25, два +15, три +8, иначе 0 |
| Длительность | От 180 минут +15, от 120 +10, от 60 +5 |
| Технология | Признак `gigabit` +10; подстрока `FTTB` в типе с учётом регистра +5 |

Критичность разрешает равенство regret, а не заменяет его. Поэтому высокий базовый приоритет сам по себе не гарантирует первое назначение.

## Локальные улучшения и два старта

`localImprove()` проверяет сохранение окон и смен и принимает уменьшение расстояния более чем на 0,05 км:

1. Перестановки соседних незакреплённых заявок внутри маршрута.
2. Перенос последней незакреплённой заявки маршрута в конец другого совместимого маршрута.
3. Один лучший обмен парой незакреплённых заявок между маршрутами.

Это ограниченные проходы, а не полный поиск до сходимости и не полный классический 2‑opt, хотя такое название встречается в подсказке интерфейса.

В утреннем режиме улучшается также копия baseline. Между ней и результатом regret‑2 выбирается план сначала с большим числом назначений, затем с меньшим расстоянием. Поэтому итоговая колонка `regret‑2` может фактически содержать улучшенный baseline. Число инженеров не является отдельным критерием этого выбора.

## Оперативное перепланирование

`schedule('operational')` сохраняет из предыдущих маршрутов работы со статусами `enroute`, `started`, `completed`: исполнитель, время и порядок закреплённой части остаются. Остальные заявки распределяются заново. Плановый час без статуса не является основанием фиксации.

Новая доступность маршрута начинается не раньше текущего времени, начала смены и окончания последней закреплённой работы. Стартовая точка — последняя закреплённая заявка либо исходная точка инженера. Фактическое время окончания пока используется для отставания, но не заменяет `planEnd` при вычислении доступности.

`schedule('auto')` выбирает утренний режим, если текущее время не позже минимума между `08:00` и положительными временами начала смен всех инженеров. Позже используется оперативный режим. `initial` всегда означает утренний расчёт.

**Оговорка сравнения:** показываемый baseline при каждом расчёте строится заново с начала смены (`operational=false`). После оперативного события он не получает тот же закреплённый префикс, что основной план. Это сравнение с новым утренним расчётом на текущих данных, а не строгий эксперимент двух оперативных алгоритмов в одинаковом состоянии.

## Показатели

| Показатель | Фактическая формула и смысл |
|---|---|
| Распределено | Число заявок минус число нераспределённых; процент округляется до целого |
| Инженеров | Число непустых маршрутов |
| Пробег | Сумма `route.distance`; в интерфейсе округляется до целых километров |
| SLA | Число назначений, у которых `planEnd` позже конца окна |
| Hard constraints | Число назначений, не проходящих `compatible()`: доступность, навык, транспорт |
| Свободный ресурс | Сумма полной длительности смен доступных инженеров минус длительности работ и переездов во всех маршрутах; отрицательный результат отображается как 0 |
| Перегружено | Число маршрутов с наложением интервалов работ либо флагом `manualOverload` |
| Время расчёта | Время функции `schedule()` до `renderAll()`, включая алгоритмы, сравнение и пояснения; без сетевого ожидания и отрисовки |
| Локальные улучшения | Число принятых перестановок/переносов/обменов выбранного варианта |

`Hard constraints = 0` не проверяет уникальность, полноту плана, все временные ограничения и достижимость с учётом дороги. После снятия инженера с линии его сохранённая завершённая работа может увеличить этот показатель из-за текущей недоступности.

Свободный ресурс не вычитает время ожидания и уже прошедшую часть дня. Почасовая матрица показывает интервалы работ, без переездов. Поэтому эти показатели нельзя читать как точное число доступных для новой заявки часов.

## Отставание и объяснения

`refreshActualDelays()` суммирует разности `фактическое окончание − плановое окончание` завершённых работ, упорядоченных по фактическому времени. Раннее завершение уменьшает сумму. Массив графика ограничен шестью значениями, при нехватке повторяется последнее. Подписи часов фиксированы и не означают точные временные отметки фактов.

`explainAssignments()` ищет альтернативу среди совместимых инженеров по времени пути от их стартовых точек. Свободное место в полном расписании альтернативы при формировании текста не доказывается. Это описание выбора, не отдельный сертификат оптимальности.
